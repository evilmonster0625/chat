@SecureInvoke — 事务安全执行模块

保证方法在数据库事务提交后「至少执行一次」的轻量级基础设施

模块：mallchat-transaction  |  定位：mallchat-tools 生态  |  技术栈：Spring AOP + MyBatis Plus + RocketMQ

模块简介

mallchat-transaction 是 MallChat 体系中解决「事务边界与业务执行解耦」问题的核心模块。它解决了一个经典分布式困境：

问题：在 Spring @Transactional 方法中，数据库提交后执行的操作（如发送 MQ 消息、调用外部 API）如果在此刻失败，事务已经提交无法回滚，导致数据不一致。

该模块通过 @SecureInvoke 注解 + AOP 切面 + 数据库记录 + 定时重试，提供了一种 轻量、无侵入的「事务后至少执行一次」 的保证机制。

核心理念：如果某个操作「必须随着事务的成功而成功」，那么不要在当前线程中立即执行它——先把执行计划持久化到数据库，等事务提交后再执行。失败了就重试，直到成功或达到上限。

设计思想

1. 先记录，后执行 —— "Write-Ahead Execution"

传统做法是在事务中直接执行操作，成功则提交、失败则回滚。但当操作本身是外部调用（MQ、RPC、文件上传）时，外部系统的成功/失败不应影响本地事务的原子性。@SecureInvoke 的做法是：先把「执行计划」作为一条记录写入数据库（和主事务同库，享受本地事务保护），待事务提交后再真正执行。这本质上是将"执行"与"事务提交"解耦。

2. At-Least-Once 语义

该模块提供的是"至少执行一次"保证，而非"恰好一次"。可能在极端情况下（执行成功但更新数据库状态失败）导致重复执行。因此，被标记的方法应当是幂等的。这是设计上的有意取舍——用偶发的重复执行换取「绝不丢失」的确定性。

3. 异步优先，同步可选

默认情况下，事务提交后的执行是异步的（提交到 Executor 线程池）。这有两个好处：

  • 调用线程不必等待方法执行，快速释放数据库连接
  • 即使方法执行较慢（如 HTTP 调用、文件处理），也不会阻塞 web 线程

同步模式供 MQ 消费等场景使用，这些场景在意链路追踪上下文（Tracing 信息绑定在当前线程），对耗时相对不敏感。

4. 指数退避重试 —— 优雅应对失败

重试间隔呈指数增长：2min → 4min → 8min → 16min……这种退避策略：

  • 避免下游系统在故障恢复时被重试洪峰压垮（Thundering Herd）
  • 短期抖动（网络闪断、连接池耗尽）在早期重试中自愈
  • 长期故障不会造成无意义的频繁轮询

5. 防重入 —— 避免无限递归

当重试机制通过反射重新执行目标方法时，该方法上的 @SecureInvoke 注解会再次触发切面。如果切面不加区分地再次记录，就会形成「执行 → 记录 → 提交 → 重试 → 执行 → 记录 → …」的无限循环。SecureInvokeHolder 通过 ThreadLocal 标记当前是否为重试调用，切面据此跳过记录逻辑，直接执行。

6. 自包含、零配置集成

通过 spring.factories 注册自动配置，任何 Spring Boot 项目只要引入此 jar 即可使用 @SecureInvoke 注解，无需 @Import、@ComponentScan 或手动配置。符合 Spring Boot 的「Opinionated Auto-Configuration」哲学。

核心数据流

一次完整的 @SecureInvoke 调用生命周期如下：

[Phase 1 — 切面拦截] ① 调用方在 @Transactional 方法中调用 @SecureInvoke 方法 ② SecureInvokeAspect 拦截： ├─ 如果 SecureInvokeHolder.isInvoking() == true → 直接 proceed()，跳过 ├─ 如果无活动事务 → 直接 proceed()，跳过 └─ 否则 ↓ [Phase 2 — 执行计划持久化] ③ 切面构建 SecureInvokeDTO（类名、方法名、参数类型JSON、参数值JSON） ④ 构建 SecureInvokeRecord（maxRetryTimes、nextRetryTime = now + 2min） ⑤ SecureInvokeService.invoke(record, async)： ├─ 保存 record 到数据库（与业务事务同一事务） └─ 注册 TransactionSynchronization.afterCommit() 回调 [Phase 3 — 事务提交后执行] ⑥ 业务 @Transactional 方法正常结束 → Spring 提交事务 ⑦ afterCommit() 回调触发： ├─ async=true → doAsyncInvoke() → Executor 线程池执行 └─ async=false → doInvoke() → 当前线程执行 ⑧ doInvoke()： ├─ SecureInvokeHolder.setInvoking() ← 防重入 ├─ 反射：SpringUtil.getBean() → 获取 Spring Bean ├─ 反射：ReflectUtil.getMethod() → 定位目标方法 ├─ 反射：JsonUtils 反序列化参数 → method.invoke() ├─ 成功 → removeRecord(id) ← 删除记录 └─ 失败 → retryRecord() ← 更新退避时间/次数/失败原因 ⑨ SecureInvokeHolder.invoked() ← 清理 ThreadLocal [Phase 4 — 定时重试（持续进行）] ⑩ @Scheduled(cron = "*/5 * * * * ?") retry()： ├─ DAO 查询条件： │ ├─ status = STATUS_WAIT (1) │ ├─ next_retry_time < now() │ └─ create_time < now() - 2min (避免刚入库的数据被拉取) └─ 对每条记录 → doAsyncInvoke() ⑪ doInvoke() 中若再次失败 → 指数退避更新 nextRetryTime ⑫ retryTimes > maxRetryTimes → status = STATUS_FAIL (2) 停止重试
关键时序保证：save(record) 与业务操作在同一个数据库事务中，因此如果业务操作回滚，执行计划记录也随之回滚——绝不会出现「事务回滚了但记录了一条要执行的假任务」的情况。

@SecureInvoke 注解

@Retention(RUNTIME) @Target(METHOD)

属性类型默认值说明
maxRetryTimes int 3 最大重试次数（含第一次正常执行）。例如默认值 3 意味着首次失败后可重试 2 次
async boolean true 是否异步执行。true 在事务提交后提交到线程池；false 在当前线程同步执行
设计意图：注解本身不定义任何"执行什么"，只声明"要保证执行"。具体行为由 AOP 切面和 SecureInvokeService 提供。这是关注点分离的体现。

SecureInvokeAspect 切面

@Aspect @Order(HIGHEST_PRECEDENCE + 1) @Component

使用 @Around("@annotation(secureInvoke)") 拦截所有标注了 @SecureInvoke 的方法。

执行逻辑

条件行为
SecureInvokeHolder.isInvoking() == true 直接执行原方法，不记录。表明这是重试调用，避免循环
无活动事务 直接执行原方法，不记录。非事务场景不需要此模块的保证
有活动事务 + 非重试 序列化方法调用 → 构建 SecureInvokeRecord → 调用 service.invoke()

序列化细节

SecureInvokeDTO:
  className    = method.getDeclaringClass().getName()
  methodName   = method.getName()
  parameterTypes = JsonUtils.toStr([paramType1.class.getName(), ...])
  args         = JsonUtils.toStr(joinPoint.getArgs())
注意：切面在捕获到 @SecureInvoke 方法后 返回 null，不返回原方法的返回值。因为实际执行被延迟到事务提交之后。调用方不应依赖 @SecureInvoke 方法的返回值。

SecureInvokeService 核心服务

@AllArgsConstructor 非 Spring Bean（由 @Configuration 手动 new）

整个模块的心脏，负责执行计划保存、事务回调注册、反射执行和定时重试。

方法清单

方法可见性说明
invoke(record, async)public保存记录 + 注册 TransactionSynchronization.afterCommit() 回调
doInvoke(record)public通过反射执行方法：获取 Bean → 定位 Method → 反序列化参数 → invoke → 成功删除 / 失败更新退避
doAsyncInvoke(record)public将 doInvoke 提交给 Executor 执行
retry()public@Scheduled(cron = "*/5 * * * * ?") 每 5 秒扫描待重试记录并异步重试
save(record)public委托 DAO 保存记录
retryRecord(record, errorMsg)private更新重试次数 + 指数退避 nextRetryTime + 失败原因。超过上限则标记 STATUS_FAIL
removeRecord(id)private执行成功后删除数据库记录

反射执行机制

doInvoke(record):
  1. SecureInvokeHolder.setInvoking()    ← 设防重入标记
  2. Class.forName(className)            ← 加载类
  3. SpringUtil.getBean(beanClass)       ← 从 Spring 容器获取 Bean（支持 AOP 代理）
  4. JsonUtils.toList(parameterTypes)    ← 还原参数类型列表
  5. ReflectUtil.getMethod(bean, methodName, paramClasses)  ← 定位 Method
  6. JsonUtils 反序列化 args             ← 还原参数值
  7. method.invoke(bean, args)           ← 真正执行
  8. 成功 → removeRecord(id)
     失败 → retryRecord(record, e)
  9. finally → SecureInvokeHolder.invoked()  ← 清理标记

指数退避算法

waitMinutes = Math.pow(RETRY_INTERVAL_MINUTES, retryTimes)
// RETRY_INTERVAL_MINUTES = 2.0
// retryTimes=1 → 2min   retryTimes=2 → 4min
// retryTimes=3 → 8min   retryTimes=4 → 16min

定时重试

@Scheduled(cron = "*/5 * * * * ?")  // 每 5 秒
retry():
  records = dao.getWaitRetryRecords()
  for each record → doAsyncInvoke(record)

DAO 查询条件:
  - status = STATUS_WAIT (1)
  - next_retry_time < now()
  - create_time < now() - 2min  （避免刚入库的数据被拉取，给事务提交留出窗口）

数据访问层

SecureInvokeRecordDao 继承 ServiceImpl<SecureInvokeRecordMapper, SecureInvokeRecord>，提供标准的 MyBatis Plus CRUD 操作和一个自定义查询方法：

getWaitRetryRecords()

查询符合条件的待重试记录：

  • status = STATUS_WAIT (1)
  • next_retry_time < now()（已经到达或超过重试时间）
  • create_time < now() - 2min（避免拉取刚刚插入、事务尚未提交的记录）
为什么需要 create_time 条件？记录在业务事务提交前就被 insert 到数据库了。如果定时任务在事务提交前就扫描到这条记录（事务可能持有锁未释放），会出现"事务还没提交就开始重试"的竞态条件。2 分钟窗口确保了事务有充足的时间完成提交。

SecureInvokeHolder — 防重入守卫

一个极简的 ThreadLocal<Boolean> 持有者，提供三个静态方法：

方法用途
setInvoking()doInvoke() 执行前调用，标记当前线程正在重试执行
isInvoking()切面中检查，若为 true 则跳过切面逻辑直接执行
invoked()doInvoke() 的 finally 块中调用，清理 ThreadLocal
为什么不用其他防重入方式？理论上可以在记录中加入一个"本次执行 ID"来实现幂等性检查，但这会引入额外的查询开销。ThreadLocal 方式零开销、零额外数据库交互，且与「当前执行必然由本次重试触发」的语义完全匹配。

MQProducer — 可靠消息发送

MQProducer 是 @SecureInvoke 最典型的使用场景。它提供两种消息发送方式：

方法注解语义
sendMsg(topic, body) 无 直接发送 RocketMQ 消息，无事务保证。如果发送时事务尚未提交，消费者可能在事务提交前就消费到数据，导致读取到不完整的状态
sendSecureMsg(topic, body, key) @SecureInvoke 通过 @SecureInvoke 保证消息在事务提交后「至少发送一次」。第三个参数 key 被设置到 RocketMQ 的 KEYS 头部，用于消息去重或追踪
实践建议：在 MallChat 项目中，所有需要在事务后发送 MQ 消息的场景都应使用 sendSecureMsg()，而非 sendMsg()。这确保了消息不会在事务提交前被消费到，也不会因为事务提交后的瞬时故障丢失。

SecureInvokeConfigurer — 线程池定制 SPI

一个函数式接口，允许应用自定义异步执行使用的线程池：

@FunctionalInterface
public interface SecureInvokeConfigurer {
    @Nullable
    default Executor getSecureInvokeExecutor() {
        return null;  // 返回 null 表示使用默认的 ForkJoinPool.commonPool()
    }
}
实现方式：实现该接口并声明为一个 Spring Bean 即可。TransactionAutoConfiguration 使用 ObjectProvider 收集所有实现，如果存在多于一个则抛出异常（防止歧义）。如果不存在，回退到 ForkJoinPool.commonPool()。

典型自定义实现：

@Bean
public SecureInvokeConfigurer myConfigurer() {
    return () -> Executors.newFixedThreadPool(4, new ThreadFactoryBuilder()
            .setNameFormat("secure-invoke-%d")
            .build());
}

通过 spring.factories 注册的 Spring Boot 自动配置类：

组件方式说明

Executor 解析逻辑

1. ObjectProvider 收集 SecureInvokeConfigurer Bean
2. 如果存在 0 个 → 使用 ForkJoinPool.commonPool()
3. 如果存在 1 个 → 调用 configurer.getSecureInvokeExecutor()
   ├─ 返回非 null → 使用自定义 Executor
   └─ 返回 null   → 使用 ForkJoinPool.commonPool()
4. 如果存在 > 1 个 → 抛出 IllegalStateException
注意：自动配置仅在模块被引入且 Spring Boot 的自动配置条件满足时生效。如果应用中存在多个 SecureInvokeConfigurer，启动时会报错——这是有意为之，避免线程池配置冲突导致不确定行为。

使用方式

1. 引入依赖

<dependency>
    <groupId>com.abin.mallchat</groupId>
    <artifactId>mallchat-transaction</artifactId>
</dependency>

引入后自动配置生效，无需任何额外配置。

2. 创建数据库表

CREATE TABLE `secure_invoke_record` (
    `id`             BIGINT AUTO_INCREMENT PRIMARY KEY,
    `secure_invoke_json` JSON    NOT NULL COMMENT '方法调用快照',
    `status`         TINYINT     NOT NULL DEFAULT 1 COMMENT '1待执行 2已失败',
    `next_retry_time` DATETIME   NOT NULL COMMENT '下次重试时间',
    `retry_times`    INT         NOT NULL DEFAULT 0 COMMENT '已重试次数',
    `max_retry_times` INT        NOT NULL DEFAULT 3 COMMENT '最大重试次数',
    `fail_reason`    TEXT        NULL     COMMENT '失败原因',
    `create_time`    DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `update_time`    DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_status_next_retry (`status`, `next_retry_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

3. 在方法上使用 @SecureInvoke

@Transactional
@SecureInvoke(maxRetryTimes = 3, async = true)
public void sendMsg(Long uid, String content) {
    // 业务逻辑——将在事务提交后执行
    rocketMQTemplate.send(topic, MessageBuilder.withPayload(content).build());
}

4. 使用 MQProducer 发送可靠消息

@Autowired
private MQProducer mqProducer;

@Transactional
public void businessMethod(Long userId) {
    // 业务操作...
    mqProducer.sendSecureMsg("topic-notify", notifyDTO, String.valueOf(userId));
}

5. 自定义线程池（可选）

@Bean
public SecureInvokeConfigurer secureInvokeConfigurer() {
    return () -> {
        ThreadPoolExecutor executor = new ThreadPoolExecutor(
            2, 4, 60, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(1000),
            new ThreadFactoryBuilder().setNameFormat("secure-invoke-%d").build()
        );
        return executor;
    };
}
最佳实践：
  • @SecureInvoke 标注的方法应当幂等——重试可能导致多次执行
  • 方法参数类型必须是 Jackson 可序列化的
  • 不要在 @SecureInvoke 方法上依赖返回值（切面返回 null）
  • DB 表务必建联合索引 (status, next_retry_time)，避免定时任务全表扫描
  • 根据业务容忍度调整 maxRetryTimes，默认 3 次（约 2+4=6 分钟的自愈窗口）

关键设计决策

为什么不用 MQ 事务消息？

RocketMQ 本身支持事务消息（半消息 + 本地事务检查），能够解决事务后发送消息的问题。但选择 @SecureInvoke 方案的原因：

  • 通用性强：不限于 MQ 发送场景，可以保证任何操作的执行（API 调用、缓存更新、文件处理等）
  • 资源友好：不依赖 MQ 代理的事务消息能力，使用本地数据库即可
  • 轻量：无需额外的 MQ 事务回查机制，一条记录 + 一个定时任务即可

为什么执行参数要 JSON 序列化到数据库？

  • 解耦：执行计划的消费者（重试任务）不依赖原始调用者的内存状态
  • 持久化：即使应用重启，待重试的任务仍然在数据库中，不会丢失
  • 可观测性：DBA / 运维可以直接查看 secure_invoke_json 字段了解待执行的任务详情

为什么切面在有事务时才生效？

如果当前没有 Spring 事务，@SecureInvoke 就直接执行方法，不做任何记录。原因：

  • 非事务场景下，方法执行失败本身就是最终结果，没有"事务已提交但操作未执行"的不一致问题
  • 避免在非事务方法上无意义地写库和调度，减少数据库和线程池开销

为什么使用 ForkJoinPool.commonPool() 作为默认线程池？

  • ForkJoinPool 是 JDK 内置的、无需额外依赖的通用线程池
  • 其工作窃取（Work-Stealing）机制适合异步执行的批量重试场景
  • 允许用户通过 SecureInvokeConfigurer 完全自定义，不强制绑定

同步 vs 异步的取舍

默认异步（async = true）的原因：

  • @Transactional 方法通常运行在 Web 请求线程中，应当尽快释放连接
  • 被保证执行的操作往往涉及外部 IO（MQ、RPC），不适合阻塞 web 线程

同步模式（async = false）的使用场景：

  • MQ 消费者中调用 @SecureInvoke 方法——消费者对耗时容忍度高
  • 链路追踪（Tracing）需要在同一线程中延续——跨线程会丢失 Trace ID

2 分钟避让窗口的意义

getWaitRetryRecords() 中 create_time < now() - 2min 条件解决了以下问题：

  • 事务未提交竞争：记录在事务提交前就已写入，定时任务可能在事务提交前就扫描到
  • 主从延迟：如果使用 MySQL 主从架构，刚写入的记录可能尚未同步到从库
  • 批量重试合理聚合：2 分钟窗口让同一批失败的任务聚合重试，减少碎片化调度

为什么不引入消息队列做重试？

引入 MQ 做重试会带来额外的复杂度：需要专门的 retry topic、死信队列、消费组配置等。@SecureInvoke 使用数据库轮询方案，对于 MallChat 这种单体应用体量来说，简单、可靠、可观测，避免了引入额外中间件的运维成本。
